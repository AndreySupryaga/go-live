# Go Live — від папки на комп'ютері до живого сайту

Мета: людина без технічного досвіду отримує робоче посилання `https://<назва>.vercel.app`,
а кожна наступна зміна публікується сама після `push` у гілку `main`.

Схема: **папка проєкту → приватний репозиторій GitHub → Vercel (нативна Git-інтеграція) → посилання**.
Vercel сам деплоїть кожен push у `main`. GitHub Actions для деплою **не використовуються**.

## Правила спілкування

- Говори мовою користувача, простими словами, без жаргону. Кожен термін пояснюй одним реченням
  (напр. «репозиторій — це папка проєкту в хмарі GitHub з історією всіх змін»).
- Вибір (назва, favicon, прев'ю) пропонуй **інструментом запитань із варіантами**
  (`AskUserQuestion` у Claude Code: 2–4 варіанти, «Інше» додається автоматично).
  Якщо такого інструмента немає — нумерований список і прохання відповісти цифрою.
- Інтерактивні входи (`gh auth login`, `vercel login`) людина робить **сама**. У Claude Code
  підкажи ввести в полі чату `! gh auth login` — команда виконається в цій сесії.
  Паролі й токени ніколи не проси й не вводь за людину.
- Нічого не публікуй публічно: репозиторій завжди `--private`.

## Крок 0. Де ми і що робимо

1. Корінь проєкту = поточна папка. **Якщо поточна папка — домашня (`$HOME`, `~`) або системна —
   зупинись** і попроси відкрити саме папку проєкту. `git init` у домашній папці заборонений.
2. Визнач режим:
   - `git remote get-url origin` вказує на GitHub **і** Vercel уже підключено
     (є `.vercel/project.json` або `vercel project inspect <назва>` знаходить проєкт) →
     **режим «Оновлення»** (див. кінець файлу).
   - Людина просить підключити свій домен → **режим «Власний домен»**; якщо сайт ще не
     опублікований — спершу кроки 1–7.
   - Інакше → **перша публікація**, кроки 1–7.

## Крок 1. Перевірка інструментів

Виконай і розбери результат:

```bash
git --version
gh --version
gh auth status
node --version        # потрібен лише для Vercel CLI
vercel --version      # може бути відсутній — це нормально
```

Якщо чогось бракує — **запропонуй встановити це самому**: назви команду для ОС людини
(`uname -s`; на Windows — Git Bash/PowerShell), попроси дозвіл і виконай її. Якщо людина хоче
зробити сама або команда потребує пароля адміністратора — дай інструкцію і чекай «готово».
Потім перевір ще раз.

| Що | macOS | Windows |
| --- | --- | --- |
| Git | `xcode-select --install` або `brew install git` | `winget install --id Git.Git -e` |
| GitHub CLI (`gh`) | `brew install gh` | `winget install --id GitHub.cli -e` |
| Node.js (для Vercel CLI) | `brew install node` або https://nodejs.org (LTS) | `winget install OpenJS.NodeJS.LTS` |
| Vercel CLI | `npm i -g vercel` | `npm i -g vercel` |

Немає Homebrew на macOS → https://brew.sh (одна команда з сайту). Після встановлення через winget
на Windows — перезапустити термінал.

**Акаунт GitHub.** Якщо `gh auth status` каже, що вхід не виконано:
1. Немає акаунта → https://github.com/signup. Найшвидше — **Continue with Google** (або Apple):
   окремий пароль не потрібен, акаунт створюється на пошту Gmail. Класичний шлях — email і пароль.
   Порадь username коротким і латиницею — він стане частиною посилань на репозиторії.
   Двофакторний захист — за бажанням, можна ввімкнути пізніше:
   Settings → Password and authentication → Authenticator app.
2. Вхід: людина вводить `! gh auth login` → GitHub.com → HTTPS → Login with a web browser.
3. Якщо `git config user.name` / `user.email` порожні — налаштуй їх (імʼя і email акаунта GitHub).

**Акаунт Vercel і зв'язка з GitHub (один раз на все життя):**
1. https://vercel.com/signup → тариф **Hobby** → **Continue with GitHub**. Так Vercel і GitHub
   одразу пов'язані, окремий пароль не потрібен. Входу через Google у Vercel **немає** —
   є GitHub, GitLab, Bitbucket і код на пошту. Якщо людина вже зареєструвалась поштою,
   GitHub усе одно треба підключити: Vercel → Settings → Authentication → Connections.
2. Дати Vercel доступ до репозиторіїв: https://github.com/apps/vercel → Configure → обрати акаунт →
   **All repositories** (простіше) або Only select repositories (тоді додавати кожен новий репозиторій).
3. Якщо є Vercel CLI: людина вводить `! vercel login` → Continue with GitHub.

**Режим деплою:**
- **A (автоматичний, рекомендований):** є Node.js і Vercel CLI + `vercel whoami` працює.
  Скіл сам створює проєкт на Vercel і підключає до нього репозиторій.
- **B (через сайт Vercel):** Node.js ставити не хочуть/не можуть. Скіл робить усе, крім одного
  кроку «Import» на сайті Vercel — його людина клацає за твоєю інструкцією.

Якщо Node є, а Vercel CLI немає — запропонуй встановити (A). Якщо Node немає — запитай:
встановити Node (A) чи зробити один крок на сайті (B).

## Крок 2. Перевірка проєкту перед публікацією

1. **Що це за проєкт:**
   - `index.html` у корені → статичний сайт, збірка не потрібна.
   - Джерело, а не сайт: `.pptx`, `.pdf`, `.docx`, папка з текстом → людина хоче **сайт із цього
     матеріалу**. Не викладай вихідний файл як є і не роби галерею скриншотів: витягни текст
     (`soffice --headless --convert-to pdf`, далі `pdftotext -layout`) і **напиши справжню
     сторінку** — заголовки, секції, списки, картки, адаптив під телефон. Вихідний файл можна
     покласти поруч як «Завантажити PDF».
   - `package.json` → фреймворк (Vite, Next.js, Astro…). Vercel визначає його сам;
     переконайся, що `npm run build` проходить локально, якщо Node є.
   - HTML-файл з іншою назвою і немає `index.html` → **перейменуй його в `index.html`**
     (інакше сайт відкриється з помилкою 404) і скажи людині, що зробив це і навіщо.
     Кілька HTML-файлів і жодного `index.html` → запитай, який з них головний.
2. **Секрети.** Шукай `.env*`, `*.pem`, `*.key`, `credentials*.json`, `service-account*.json` і рядки
   на кшталт `sk-`, `AKIA`, `ghp_`, `api_key`, `apiKey`, `secret`, `token` у коді:
   ```bash
   git ls-files 2>/dev/null; ls -la
   grep -rInE "(sk-[A-Za-z0-9_-]{20,}|AKIA[0-9A-Z]{16}|ghp_[A-Za-z0-9]{30,}|api[_-]?key|secret|password)\s*[:=]" \
     --exclude-dir={node_modules,.git,dist,.next} . | head -20
   ```
   Знайшов ключ у файлі, який піде в браузер → **зупинись і поясни**: навіть у приватному
   репозиторії ключ у коді сайту бачить кожен відвідувач. Ключі — у Vercel → Settings →
   Environment Variables і лише в серверному коді.
3. **`.gitignore`** — створи або доповни:
   ```
   .DS_Store
   Thumbs.db
   node_modules/
   dist/
   .next/
   .vercel
   .env*
   !.env.example
   .claude/
   .agents/
   ```
   Службові папки агента (`.claude/`, `.agents/`) у репозиторій не потрапляють.
4. Великі файли: відео/архіви > 50 МБ у git не додавай (GitHub відхиляє > 100 МБ) —
   запропонуй стиснути або винести на YouTube/Vimeo.

## Крок 3. Назва = адреса сайту (обов'язкове підтвердження)

Назва однакова для репозиторію GitHub, проєкту Vercel і адреси `https://<назва>.vercel.app`.

1. **Базова назва** — з назви папки проєкту: латиниця (транслітеруй кирилицю:
   «Мій Сайт Йога» → `miy-sayt-yoga`), малі літери, пробіли і `_` → `-`, лише `a-z 0-9 -`, до 50 символів.
2. **Кандидати** (6–8): базова назва; коротша версія; змістовні варіанти з вмісту сайту
   (імʼя/бренд + `-site`, `-online`, `-landing`, тема + місто тощо); базова + `-2`, `-3`.
3. **Перевір усі разом** (скрипт поруч із цим файлом):
   ```bash
   bash "<шлях-до-скіла>/scripts/check-name.sh" name1 name2 name3 ...
   ```
   `free` — вільна скрізь; `taken` — зайнята (причина в третій колонці); `unknown` — перевір ще раз.
4. **Запитай людину завжди**, навіть якщо базова назва вільна. Варіанти — лише `free`, до 4 штук,
   першим — базова назва, якщо вона вільна (з позначкою «рекомендовано»); в описі кожного варіанта —
   повна адреса `https://<назва>.vercel.app`. Якщо базова назва зайнята — прямо скажи це
   і чому (причина з колонки 3).
5. Людина вписала свою назву («Інше») → нормалізуй, перевір тим самим скриптом. Зайнята → поясни
   і знову запропонуй вільні варіанти.

## Крок 4. Favicon і прев'ю посилання в месенджерах

Мета: коли посилання надсилають у Telegram/WhatsApp/Viber/Facebook, видно заголовок, опис і картинку,
а у вкладці браузера — іконку.

1. **Favicon** — запитай із варіантами:
   - «У мене є картинка» → людина дає шлях; скопіюй у корінь як `favicon.png` (або `.ico/.svg/.jpg`).
     Квадратна, від 64×64; для iPhone додатково `apple-touch-icon.png` 180×180, якщо є PNG.
   - «Згенерувати з емодзі» → запропонуй 3 емодзі за темою сайту, створи `favicon.svg`:
     `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 100 100"><text y=".9em" font-size="90">🚀</text></svg>`
   - «Згенерувати з літери» → `favicon.svg` із першою літерою бренду на кольоровому квадраті
     (колір — основний колір сайту).
   - «Пропустити».
2. **Заголовок і опис** — склади з вмісту сторінки 2 варіанти (title до 60 символів, description
   до 160) і запитай із варіантами. Мова — мова сайту.
3. **Картинка прев'ю** (1200×630) — запитай із варіантами:
   - «Скріншот першого екрана сайту» → якщо є Chrome/Chromium:
     ```bash
     # macOS: CHROME="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
     # Windows (Git Bash): CHROME="/c/Program Files/Google/Chrome/Application/chrome.exe"
     "$CHROME" --headless=new --hide-scrollbars --window-size=1200,630 \
       --screenshot="$PWD/og-image.png" "file://$PWD/index.html"
     # macOS: стиснути в JPEG (WhatsApp не показує важкі картинки; ціль ≤ 300 КБ)
     sips -s format jpeg -s formatOptions 80 og-image.png --out og-image.jpg && rm og-image.png
     ```
     Покажи результат людині (відкрий файл), перш ніж іти далі.
   - «У мене є картинка» → скопіюй як `og-image.jpg`/`.png`; попередь, якщо не 1.91:1 або > 1 МБ.
   - «Без картинки».
4. **Теги** — у `<head>` `index.html` одразу після `<meta charset…>` (для Next.js — через
   `metadata` в `app/layout`, для Vite — у кореневому `index.html`). Існуючі однойменні теги
   **замінюй**, не дублюй. Адреси картинок — **лише абсолютні** (відносні месенджери ігнорують):
   ```html
   <meta name="viewport" content="width=device-width, initial-scale=1">
   <title>ЗАГОЛОВОК</title>
   <meta name="description" content="ОПИС">
   <link rel="icon" href="/favicon.svg" type="image/svg+xml">
   <link rel="apple-touch-icon" href="/apple-touch-icon.png">
   <link rel="canonical" href="https://НАЗВА.vercel.app/">
   <meta property="og:type" content="website">
   <meta property="og:url" content="https://НАЗВА.vercel.app/">
   <meta property="og:title" content="ЗАГОЛОВОК">
   <meta property="og:description" content="ОПИС">
   <meta property="og:image" content="https://НАЗВА.vercel.app/og-image.jpg">
   <meta property="og:image:width" content="1200">
   <meta property="og:image:height" content="630">
   <meta name="twitter:card" content="summary_large_image">
   ```
   Рядки для відсутніх файлів (apple-touch-icon, og:image) не додавай. `viewport` — лише якщо його немає.

## Крок 5. Приватний репозиторій на GitHub

```bash
git init -b main 2>/dev/null || { git init && git checkout -b main; }
git add <конкретні файли й папки проєкту>      # не «git add .» наосліп — спершу подивись git status
git status                                      # переконайся: немає .env, ключів, node_modules
git commit -m "Перша публікація сайту"
```

- **Режим A:** створи репозиторій **без push** — push зробимо після підключення Vercel,
  щоб саме він запустив перший деплой:
  ```bash
  gh repo create НАЗВА --private --source=. --remote=origin
  ```
- **Режим B:** створи й одразу завантаж:
  ```bash
  gh repo create НАЗВА --private --source=. --remote=origin --push
  ```

Перевір: `git remote -v` → `github.com/<user>/НАЗВА`.

## Крок 6. Підключення до Vercel і перший деплой

**Режим A (Vercel CLI):**
```bash
vercel link --yes --project НАЗВА       # створює проєкт на Vercel
vercel git connect --yes                # підключає GitHub-репозиторій → автодеплой з main
git push -u origin main                 # цей push запускає перший production-деплой
```
- Якщо в людини кілька команд у Vercel і `link` просить scope — запитай, яку взяти, і додавай `--scope <team>`.
- Помилка `git connect`: **`You need to add a Login Connection to your GitHub account first`** —
  акаунт Vercel створено через Google або пошту, і GitHub до нього не прив'язаний. Виправлення:
  Vercel → аватар → Settings → **Authentication** → Connections → додати **GitHub**. Далі повтори
  `vercel git connect --yes`. **Не пропускай цей крок мовчки:** без нього push у GitHub не
  запускає деплой.
- Помилка `git connect` про доступ до репозиторію → GitHub-застосунок Vercel не має доступу:
  https://github.com/apps/vercel → Configure → додати репозиторій; повтори `vercel git connect --yes`.
- Якщо push каже «Everything up-to-date» і деплой не з'явився → `vercel deploy --prod` один раз
  (далі все піде автоматично).

**Режим B (сайт Vercel)** — дай людині інструкцію й чекай «готово»:
1. Відкрий https://vercel.com/new
2. Import Git Repository → знайди `НАЗВА` → **Import** (якщо репозиторію немає в списку —
   «Adjust GitHub App Permissions» і дай доступ).
3. Project Name — **точно `НАЗВА`**. Framework Preset: для простого HTML — **Other**, для
   фреймворку Vercel визначить сам. Нічого більше не змінюй.
4. **Deploy** → дочекайся конфетті.

## Крок 7. Перевірка (не звітуй про успіх без неї)

```bash
# чекати до ~3 хвилин, поки сайт відповість 200 (запускай у фоні, не блокуй розмову)
for i in $(seq 1 36); do
  code=$(curl -s -o /dev/null -w "%{http_code}" https://НАЗВА.vercel.app/)
  [ "$code" = 200 ] && break; sleep 5
done; echo "site: $code"
curl -s -o /dev/null -w "favicon: %{http_code} %{content_type}\n" https://НАЗВА.vercel.app/favicon.svg
curl -s -o /dev/null -w "og-image: %{http_code} %{content_type}\n" https://НАЗВА.vercel.app/og-image.jpg
curl -s https://НАЗВА.vercel.app/ | grep -E 'og:(title|image)'
```

- Сайт 2–3 хвилини віддає `404`, а `vercel ls НАЗВА` не показує деплоїв → майже напевно не
  спрацював `vercel git connect` (див. помилку про Login Connection вище). Зроби деплой командою
  `vercel deploy --prod --yes` і **скажи людині**, що автодеплой з push не працюватиме, доки вона
  не прив'яже GitHub у Vercel.
- Публікуєш сторінку з картинками (галерея, слайди, фото)? Постав у CSS `aspect-ratio` або
  атрибути `width`/`height` — інакше сторінка «стрибає», поки картинки вантажаться.
- `401` замість `200` → увімкнено Deployment Protection: Vercel → Project → Settings →
  Deployment Protection → **Vercel Authentication: Disabled** для Production. Або в режимі A:
  `vercel project protection disable НАЗВА --sso`.
- Адреса відрізняється від `НАЗВА.vercel.app` (Vercel додав суфікс) → знайди реальну в
  `vercel project inspect НАЗВА` або Project → Domains, **онови абсолютні адреси в og-тегах**,
  закомітуй і запуш.

## Що сказати людині наприкінці

1. Посилання на сайт (і що воно відкривається).
2. **Як оновлювати:** «змініть файли й скажіть мені "опублікуй зміни"» — або самі:
   `git add … && git commit -m "…" && git push`. Через ~30–60 секунд зміни онлайн.
   Невдалу версію можна відкотити: Vercel → Deployments → попередній деплой → Instant Rollback.
3. **Прев'ю:** перевірити, як виглядає посилання — https://www.opengraph.xyz. Telegram кешує прев'ю:
   якщо змінили картинку — надіслати посилання боту @WebpageBot.
4. **Чесно про безкоштовність:** тариф Vercel Hobby — для особистих і некомерційних проєктів.
   Для сайту, який продає послуги, — Vercel Pro (≈20 $/міс) або перенести на хостинг, що дозволяє
   комерційне використання безкоштовно (напр. Cloudflare Pages).
5. **Власний домен** (опційно): запитай, чи хоче людина адресу на своєму домені. Так → розділ
   «Режим "Власний домен"» нижче.

## Режим «Оновлення» (проєкт уже опублікований)

1. `git status` → покажи людині, що змінилось, простими словами.
2. Перевірка секретів (крок 2.2) для нових файлів.
3. `git add <змінені файли>` → `git commit -m "<що змінено, по-людськи>"` → `git push`.
4. Крок 7 (перевірка) для реальної адреси сайту.
Назву, favicon і теги не чіпай, якщо не просили.

## Режим «Зміна адреси»

Людина просить іншу адресу («зміни адресу сайту на …»): усе робиться з чату, заходити
у Vercel і GitHub не треба.

1. Нова назва — перевір скриптом `check-name.sh` (крок 3) і підтверди вибір запитанням.
2. Перейменуй проєкт Vercel і репозиторій, онови remote:
   ```bash
   vercel project rename СТАРА НОВА          # режим A; у режимі B: Vercel → Settings → General → Project Name
   gh repo rename НОВА --yes                  # у папці проєкту; remote оновлюється автоматично
   ```
3. Онови абсолютні адреси в тегах (`canonical`, `og:url`, `og:image`), закомітуй, запуш.
4. Перевір крок 7 на новій адресі. Скажи, що стара адреса більше не працює.

## Режим «Власний домен»

Сайт лишається на Vercel, домен лише вказує на нього. Людина платить тільки реєстратору за домен;
хостинг окремо не оплачується і переносити сайт не треба. (Правило Hobby щодо комерційного
використання від домену не змінюється.)

1. **Домен уже куплений?** Ні → поясни: купити в будь-якого реєстратора (≈ 10–15 $/рік за .com),
   бажано там, де вже є акаунт. **Не купуй за людину** і не вводь платіжні дані — це її рішення й гроші.
2. **Додати домен у проєкт Vercel** (проєкт уже опублікований, кроки 1–7 пройдені):
   - Режим A: `vercel domains add ДОМЕН` і `vercel domains add www.ДОМЕН` у папці проєкту.
   - Режим B: Vercel → Project → Settings → Domains → Add → ДОМЕН (Vercel сам запропонує www-редирект).
   Рекомендуй один головний варіант: `www.ДОМЕН` перенаправляє на `ДОМЕН`
   (Settings → Domains → www → Redirect to).
3. **Які записи потрібні:** `vercel domains inspect ДОМЕН` (і для www) або картка домену в Vercel.
   Беремо **точні значення з Vercel**, а не з пам'яті: вони бувають індивідуальні для проєкту.
   Типово: `A` для `@` і `CNAME` для `www`.
4. **Внести записи в кабінеті реєстратора** — запитай із варіантами:
   - **«Налаштуй за мене в браузері»** — якщо доступні інструменти Claude in Chrome
     (`mcp__claude-in-chrome__*`; вмикаються `claude --chrome` або `/chrome`, потрібні розширення
     Claude in Chrome і план Pro/Max/Team/Enterprise). Порядок:
     1. Спитай, де куплено домен; відкрий сайт реєстратора в **новій вкладці**.
     2. Вхід, 2FA і CAPTCHA людина робить **сама** — зупинись і чекай «увійшов».
        Паролі й коди не вводь і не проси в чаті.
     3. Знайди керування DNS цього домену. **Спершу покажи людині поточні записи і план змін**
        («додам A @ → …, CNAME www → …; видалю A @ → 1.2.3.4 парковки реєстратора») і чекай «так».
     4. Додай/зміни лише `A @` і `CNAME www`. Конфліктні `A`/`AAAA` на `@` і `CNAME`/`A` на `www`
        (зазвичай «парковка» реєстратора) — замінюй тільки після підтвердження.
     5. **Ніколи не чіпай** `MX` (пошта), `TXT` (SPF/DKIM, підтвердження Google тощо), `NS`;
        не змінюй nameservers і не вмикай/вимикай DNSSEC без прямого прохання.
     6. Збережи, зроби скриншот результату і покажи людині.
   - **«Дай інструкцію, зроблю сам»** — таблиця записів (Тип / Ім'я / Значення) і загальний шлях:
     «кабінет реєстратора → Домени → ДОМЕН → DNS / Керування DNS-записами → Додати запис».
     Те саме попередження про MX і TXT.
5. **Перевірка** (у фоні; DNS зазвичай оновлюється за хвилини, інколи до кількох годин):
   ```bash
   vercel domains inspect ДОМЕН          # режим A: чекати, поки конфігурація стане валідною
   dig +short ДОМЕН A; dig +short www.ДОМЕН CNAME   # Windows без dig: nslookup ДОМЕН
   curl -sI https://ДОМЕН | head -1       # 200 (сертифікат HTTPS Vercel видає сам)
   ```
   У режимі B — Vercel → Settings → Domains показує **Valid Configuration**.
6. **Оновити теги:** `canonical`, `og:url`, `og:image` → `https://ДОМЕН/…`; закомітуй і запуш.
   Скажи, що адреса `назва.vercel.app` теж продовжує працювати.

## Чого не робити

- **Не робити сайт із картинок.** Сторінка, зібрана зі скриншотів слайдів або зі сторінок PDF, —
  це не сайт: її не можна прочитати з телефона, у ній немає тексту для пошуку й посилань.
  Завжди витягуй текст із джерела і верстай справжню сторінку; сам PDF додавай окремим
  файлом із кнопкою «Завантажити». Картинками можна публікувати лише те, що картинками і є:
  фото, ілюстрації, галерею робіт.
- Не створювати публічних репозиторіїв і не робити репозиторій публічним.
- Не запускати `git init` / `git add` у домашній папці чи поза коренем проєкту.
- Не комітити `.env`, ключі, `node_modules`, `.vercel`.
- Не створювати GitHub Actions для деплою — деплоїть сам Vercel.
- Не вводити паролі/токени за людину і не просити їх у чаті.
- Не повідомляти «готово» без кроку 7.
- Не купувати домени, не вводити паролі/2FA/платіжні дані в браузері, не чіпати MX/TXT/NS-записи.
